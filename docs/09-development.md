# 项目与开发规范

类型：开发参考。本页定义人和 Codex 在此仓库工作的流程；可执行命令以 package.json 为准。

## 仓库与任务边界

当前为独立单包目录。只有真正需要独立版本或运行时的模块才拆成包。不要依赖同级 DeepSeek Harness checkout、复制其 node_modules，或使用本机绝对路径作为构建前提。

开始任务先明确可观察目标、所属模块和验收方式。代码存在时查看工作区差异；使用 rg 定位已有实现与调用者。跨模块改动先检查接口、消费者、Schema、持久化和对应文档，避免只改一端。

实现从一个完整行为切片开始：入口 → 业务 → 实际依赖边界 → 输出 → 验证。回报里区分文件已建立、代码已实现、离线检查通过、真实网络通过、发布产物通过。待执行清单或固定响应不构成运行证据。

## 配置与契约

固定安全/准入规则不能配置关闭；部署参数经校验可调整；工具输入受部署上限限制。非法配置在最早能确定的阶段报错，不悄悄用更宽松配置继续执行。完整规则见 [架构](03-architecture.md)。

对外字段先修改 schemas，再改生成类型/映射、实现、示例和回放。精简显示与结构化结果要表达同一状态。每个字段标明单位、是否 nullable、未知值与截断含义，兼容性见下节。

## Git 与 PR

创建 Git 仓库后主分支建议为 main，任务分支采用 `feat/主题`、`fix/主题`、`docs/主题` 或 `chore/主题`。不在其他项目仓库执行初始化、切换或清理操作。公开仓库的创建与推送由用户明确授权，具体远程和验证记录以发布结果为准。

提交采用 `type(scope): 具体结果`，如 `feat(search): distinguish blocked upstream responses`。一个提交或 PR 围绕一个可评审目标；文档和验证与行为一起提交。不要自动提交用户未纳入任务的改动。

PR 描述说明触发条件、改变后的行为、设计取舍、实际验证和剩余风险。可用 [PR 模板](../.github/PULL_REQUEST_TEMPLATE.md)。不使用“全部测试通过”代替具体检查，不把本地测试写成 CI 结果。发布包、push、部署和其他对外操作按任务授权执行，已授权的常规步骤不重复询问。

## 依赖与自动化修改

依赖策略由 [技术栈](07-technology-stack.md) 维护。不要手写完整 HTTP 客户端、HTML 解析器或 MCP 协议栈；也不要为了小功能增加整套框架。新增依赖须指出实际用途和资源成本。

Codex 修改检查脚本时，除了有效输入通过，还应证明一个对应非法输入会失败；在临时副本验证，不损坏真实工作区。不要通过批量刷新快照、扩大 ignore 或降低约束让红灯变绿。重试要针对明确原因，不反复跑相同失败命令期待偶然通过。

## 版本与存储演进

package version、工具 schema_version、数据库 schema_version 和快照格式版本各自独立。发布前草案允许协调修改；改 wire 字段时所有消费者和示例同改，不能维护两套相互矛盾的字段。

首个版本发布后按 SemVer 管理 npm 包；影响调用方的字段删除或语义改变需要明确兼容方案与版本提升。数据库即使处于预发布阶段也不能静默重置：提供显式迁移或明确不兼容错误，任何清空由用户指令决定。

ADR 的 accepted 表示设计已经采用，不等于功能已运行；完成与验证状态放在实施清单和 verification。修改既有决策先读其替代方案，避免每个 Agent 重新争论同一问题。

## 发布要求（M1 起逐步实现）

发布包前，从干净目录安装打包产物，使用 plain Node 启动声明 bin，通过真实 MCP client 做工具发现与调用，并验证 parser worker 可加载。限制 package files 清单，排除 data、录制正文、临时文件和开发凭据。实际包许可及第三方通知在首次对外发布前确定，当前 package 保持 private。

计划 CI 在 Linux 执行确定性检查；Mac ARM64 完成开发验证，Windows 支持只在对应产物实际测试后声明。实时搜索不作为普通 PR 的不稳定阻塞项，但修改 Provider 后必须补独立 live 证据；缺环境标记未测，不算成功。
