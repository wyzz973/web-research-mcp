# v2 设计

状态：**M0 已实现，版本 2.0.0-alpha.1**（2026-09-21，分支 `v2`）。本目录描述从零开始的新设计；旧的 SearXNG 实现保留在标签 `legacy-v0.5.0`，不再是本分支的一部分。实现进度与验证方式见文末「实现状态」。

## 为什么重新设计

1. **来源策略变了**。旧项目只允许免 Key 的来源，并把这条规则写成了配置常量和测试断言。现在的决定是：付费 API、厂商的匿名免 Key 档、官方免 Key API、网页抓取、自建端点都可以接入；不接入国内搜索引擎。
2. **后端形态变了**。旧项目必须自建 SearXNG（Python 或 Docker，Windows 上只能用 Docker）。新设计是进程内的多来源适配器，不需要 Python、Docker 和原生编译。
3. **工具契约要为模型重写**。旧契约面向前端展示和人工验收：每条结果约 560–970 token，`websearch` 有 13 个参数。新契约只有两个工具，默认输出小一个数量级。

## 重点

用户明确的重点是把 **`web_search` 和 `web_fetch` 这两个工具设计到对大模型真正好用**。其余部分（来源、路由、缓存、成本）都是为这两个工具服务的。

两个工具的分工：

| 工具 | 定位 | 要做到 |
| --- | --- | --- |
| `web_search` | 广泛搜索：在全网范围内找候选来源。不抓页面 | 搜得好（覆盖广、重复少）、搜得快（中位 1–2 秒）、搜得准（靠前的就是要找的，摘录足够判断） |
| `web_fetch` | 阅读指定内容，找证据：读模型指定的一个或几个页面，拿回能引用、能复核的逐字原文 | 逐字、可定位、可复核、可续读 |

## 已经确定的事

- 只暴露两个工具：`web_search`、`web_fetch`。引文校验通过 `web_fetch` 的 `find` 完成，不单独设工具。
- `web_search` 可以指定返回条数：`max_results` 默认 10，最多 50。默认预算 5,000 token；`web_fetch` 默认 8,000 token。单次上限默认 10,000，可由服务端配置调高。
- `web_search` 默认用一个来源，结果不可靠时自动补一个并融合；`deep` 才并行多个来源。每个匿名来源每天有自我限额。
- 设计经过一轮对抗审计（Opus）。采纳的结论：预算同时限制 token 和字符；`ref` 只用全称；游标绝不触发上游；不可信区块的结束标记带一次性 `nonce`；不把查询串长度检查说成防外泄；M0 必须带 `doctor` 命令、server `instructions`、robots.txt 与每主机限速。
- 在本仓库的 `v2` 分支重建；旧代码从该分支移除，历史保留在标签 `legacy-v0.5.0`。
- TypeScript、Node 22 及以上，无原生依赖。
- 不在内部调用大模型；不绕过验证码、付费墙和登录；不接入国内搜索引擎。

## 待确认

这三项先按下面的默认值实现，审计员对三项都表示赞成（第 2 项有条件），用户可以推翻：

1. MCP 默认只返回给模型看的文本；`WEB_RESEARCH_MCP_OUTPUT=json` 改为返回结果对象。
2. 厂商的匿名免 Key 档默认开启，条件是：`doctor` 和 README 明确告知查询发往哪几家公共端点、请求带包名版本的 User-Agent、每个来源每天自我限额、失败不重试。`WEB_RESEARCH_ANONYMOUS_SOURCES=0` 可以关闭。
3. `web_fetch` 默认允许抓取任意公开 URL；严格模式放到 M1。

**截至提交 `09e96a5`（2026-09-21 下午）仍未了结的事**：

- **「恶意页面不能拖垮进程」这一类没有关闭。** 今天已经是第四轮了：括号配对；空行连串与深层嵌套列表；内存放大、重复编号的标题、括号组成的标题、单个巨型段落；元素嵌套深度。每一轮都是换一种输入形状就暴露出来，修好的只是被想到的那些形状。现有的防线是：比值测试覆盖的二十多种形状、各处的规模上限（折叠 200 万字符、目录 2 万个标题、命中 1 万处、DOM 100 层、源码 1000 层、HTML 3 MB）、提取 worker 的 10 秒超时与 512 MB 堆上限。
- 提取里**第三方库**的慢路径未修：超大表格（8,333 行约 7 秒、16,666 行约 33 秒）、一段里上千个图片、输出里极长的一段空白。都在可终止的 worker 里，被超时兜住，表现为这一页诚实地以 `timeout` 结束；代价是真实的超大表格页读不了，恶意页面能白白烧掉 10 秒 CPU。
- 3 MB 的 HTML 上限与 10 秒提取预算不自洽：1 MB 到 3 MB 之间某些形状的**正常**页面会通过闸门却注定超时。不下调上限是因为 RFC 9110（1.13 MB、1.6 秒）是冒烟测试里的真实页面，下调会把它挡在外面。
- 第八轮对抗审计（复核不可见字符整类基底与嵌套守卫）**尚未返回**。
- 未知参数名仍会出现在 `notes` 里（最多 5 个，只保留 `[A-Za-z0-9_]`，各截到 32 字符），有意保留。
- `robots.txt` 因服务器错误或超时取不到时放行（与 RFC 9309 对爬虫的要求不同），是否改为严格遵循由项目所有者决定。

自上次更新以来已了结：第七轮审计的两条必须修。其一，不可见字符的基底原本是**手写枚举**，漏掉了 29 个格式字符（阿拉伯数字标记、Kaithi、16 个埃及象形文字控制符），审计员用它们把一条 66 字符的指令原样传了过去、原样解码回来；现在基底是 Unicode 的格式字符整类，手写部分只留「类里没有」的，例外规则移到整类匹配之前（连接符本身也属于该类，否则轮不到判断），并改为对全部 110 万个码点做性质断言，不再靠人手维护清单。其二，元素嵌套的超线性：13 KB 的页面曾占用一个抓取槽 16.6 秒并只产出一个字符，40,000 层时解析器本身就耗尽整个期限；现在解析后量 DOM 层级（上限 100，依据是实测的真实页面：GitHub 39、Node 文档 19、RFC 9110 13），解析前先在字节层面读一遍源码嵌套（上限 1000，空元素与自闭合标签不计），三档实测分别降到 0.4、0.2、0.2 秒，真实页面的输出逐字未变。附带修掉一处：极深文档在 `finally` 里拆解时栈溢出，那个异常会把拒绝的结论顶掉。折叠缓存的键加上了源文长度。CI 因我把新测试按本机规模编写而红过两轮（一个撑爆内存、一个超时），现在全量测试在 1 GB 堆下通过。在已推送的版本上复现并修复了一个内存放大（100 万个 U+FDFA 的 3 MB 页面让主进程多占 935 MB，修复后
